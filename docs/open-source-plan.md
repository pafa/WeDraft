# WeDraft 开源与维护安排

这是首次公开的建议与准备清单，不代表已经公开、授予许可证或发布软件。当前仍执行现有的[本地 Git 管理规则](git-workflow.md)，`pafa/WeDraft` 作为私有源码备份；公开前须确认目标仓库、许可证、具体源版本和发布范围。

## 一个产品仓库，多个入口

继续在现有项目完成初版，共同维护排版规则、格式与测试。网页、CLI、MCP、Skill 放在同一个源码仓库，插件将来只做宿主安装包装。

| 目录 | 职责 |
| --- | --- |
| `packages/core` | 可复用的文章输入、检查、渲染与文章包 API。 |
| `packages/article-*`、`wechat-renderer`、`validation` | 现有解析、数据模型和模板实现。 |
| `apps/web` | 手工编辑、预览、本机草稿与文章包进出。 |
| `apps/desktop` | Mac 应用及首版复用的编辑器组件；网页构建仍需要这些组件源码。 |
| `packages/cli`、`packages/mcp` | 同一个核心的命令行与 AI 工具入口。 |
| `skills/format-with-wedraft` | 流程说明，避免复制排版实现。 |

暂不拆成多个独立 Git 仓库。共享组件可随维护需要抽成 UI 包，不应复制后在两处各改一份。

## 首次如何公开

建议保留现有私有历史，从**审阅通过的确定版本**生成干净的公开初始源码。公开后只维护一个产品主线；旧私有库保存历史归档，不长期维护第二套产品代码。新公开仓库的名字与远端地址在正式操作前确定。

另一种方式是直接将现有仓库改为公开，但它需要审查所有可见分支、标签、历史和 Actions 日志。GitHub 明确说明转公开会公开代码与工作流日志，公众也可以 fork；之后转回私有无法撤回已经产生的公开副本。[GitHub 可见性说明](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/managing-repository-settings/setting-repository-visibility)

首次公开要交付一份可审阅的发布候选：

1. 源文件白名单与完整 diff；排除文章数据库、私稿、图片缓存、导出文件、安装包、本机路径与凭据。
2. 自有代码、图标、样稿、模板素材和依赖的许可盘点；保留必须的第三方声明。
3. 确认 LICENSE。以方便集成和商用为目标，可考虑 MIT：允许商业使用、修改和分发，要求保留版权与许可声明，也允许闭源衍生产品。不能把“必须开源所有衍生版本”理解为 MIT 的条件。[MIT 说明与原文](https://choosealicense.com/licenses/mit/)
4. README、上手示例、CONTRIBUTING、问题模板、SECURITY 联系方式和变更记录；只能填写真实可用的维护入口。
5. 干净环境安装、核心与传输测试、网页构建和浏览器交接验收；明确尚未验证的宿主和微信兼容性。
6. 维护者批准精确源版本、目标公开仓库与分发范围后，再执行公开推送、演示站部署或包发布。

## 公开后怎样管理

外部使用者提交 Issue 或 fork 后提出 PR；维护者决定需求是否进入范围，AI 可以实现、检查和整理审阅材料，合并及正式发布仍由维护者决定。一项改动围绕一个目标，核心行为改变必须同时检查网页、CLI 和 MCP。

公开仓库可以逐步启用 PR 检查与维护者审核，但这些是公开协作阶段的新规则，不会追溯成为当前私有开发的额外完成条件。初期只保留必要的安装、类型、测试与构建检查；不从外部贡献者提交中执行带生产凭据的发布任务。

问题按缺陷、功能、模板、文档归类；优先处理内容丢失、图片丢失、格式不兼容和导入失败。没有维护承诺的功能不写进产品首页。漏洞报告使用届时确认的私密渠道，不要求用户在公开 Issue 贴文章或账号信息。

## 版本与发布

新网页、core、CLI、MCP 初期按一个工具集版本协调，当前开发标记为 `0.1.0`；Mac 已有基线是 `1.1.2`，本次不据此宣称桌面新版本已经发布。文章包 `schemaVersion` 与模板 `templateVersion` 单独记录，兼容性变化要明示。

一次正式发布关联一个确定源码提交、变更说明、测试记录以及产物校验和。演示站与可下载工具使用这一版本；开发分支改动不会自动上线。出现问题发布修复版本或切回保留的旧站点产物，不覆盖旧标签与旧安装包。

首版分发可先采用源码安装 + 静态演示站，后续再发布 npm 工具包和宿主插件。当前所有新包仍设 `private: true`，用于防止误发；公开前需落实真实包名、许可证、构建文件和依赖检查。

## 演示站与数据

网页可部署为静态网站，文章编辑和草稿保存在用户浏览器；无需为演示站增加账户或文章数据库。说明同源存储、清除数据的影响和文章包备份方法。远程图片仍会请求来源网站，AI 宿主也有自己的数据处理规则，不能笼统承诺所有流程绝对离线。

演示站与 npm 包需要各自的发布权限和凭据，但这些运营配置不进入源码。托管服务访问日志与网站策略需在选定服务商后据实说明。后续如需远程 MCP，再单独设计认证、限流、存储期限和费用；它不是本地 MCP 首版的隐含能力。
